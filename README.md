## About

I work with engineering and operations leadership to move AI from prototype to production system.

Most AI initiatives fail on a single axis. They perform in a controlled demo and drift under real load, real edge cases, and real users. The cause is rarely the model — it is the absence of engineering discipline around it. My engagements target that gap: bounded scope, typed interfaces between components, deterministic orchestration wrapped around non-deterministic inference, and evaluation harnesses that surface regressions before production does.

I work independently. The person who scopes the engagement is the person who architects it, builds it, and hands it over — with no translation loss between those stages. Based in Paris, operating in English and French across European and North American time zones.

## What I build

**Agents.** Task-scoped LLM systems with defined input and output schemas, deterministic routing, bounded tool access, and explicit fallback chains. Built against a specification — not open-ended chat surfaces.

**Automations.** Removal of high-volume manual work: intake processing, classification, extraction, triage, report generation. Scoped by measured cost and volume, instrumented for audit from the first commit.

**Orchestration pipelines.** Multi-step flows across models, APIs, and internal services, with explicit state, retry semantics, defined degradation paths, and observability at every stage boundary.

**Internal tools.** The operating layer teams need around the above: review queues, evaluation runners, diagnostic utilities, and dashboards that make system behaviour legible to the people accountable for it.

## Methodology

Four phases. Each produces a written artifact. No phase begins before the previous one is signed off.

| Phase | Objective | Deliverable |
|---|---|---|
| **1 · Diagnostic** | Map the existing process, quantify volume and cost, and separate what is automatable from what is not — stating the difference plainly. | Findings document, scoped opportunity list with estimates, feasibility assessment. |
| **2 · Architecture** | Define components, data contracts, control flow, failure modes, and acceptance criteria before implementation begins. | Technical specification, interface definitions, evaluation criteria. |
| **3 · Integration** | Build against the specification and wire into existing systems. Tests and instrumentation are written alongside, never retrofitted. | Working system, test suite, evaluation harness, integration documentation. |
| **4 · Deployment** | Ship under controlled rollout, measure against the criteria fixed in phase two, and transfer full operational ownership. | Production deployment, runbook, handover session. |

The sequence is the product. Skipping the diagnostic is how organisations automate a process that should have been eliminated.

## Principles

**Predictability over capability.** A narrow system that behaves consistently is worth more than a broad one that occasionally impresses. Non-determinism stays contained at the model boundary and never enters the control flow.

**Testability is a design constraint, not a phase.** A component that cannot be tested in isolation is not correctly specified. When tests are hard to write, the architecture is wrong — not the test.

**Data contracts are explicit.** Every module boundary carries a defined schema. Inputs are validated, outputs are typed, and violations fail loudly rather than propagating downstream as silent corruption.

**Evaluation precedes deployment.** Subjective assessment does not scale and does not survive a team change. Every system ships with a fixed evaluation set and stated pass criteria, so changes are measured rather than debated.

**Handover assumes I am gone.** A system only one person understands is a liability. Documentation is part of the deliverable, not a courtesy appended to it.
